# Phase 6: Project Package For TRICS

Implemented on 2026-11-02 for the TPID "package" demonstration requested ahead of
the CADLogic meeting. Step 6 (**Project Details**) now builds a zip file that an
AI-assisted CAD system (TRICS) can use to design the roof to the performance
specification. Everything is produced in the browser; no backend, Gemini or
external service is called. The ROI plan's non-goal of "CAD geometry, or DXF
exports" ([ROI plan](ROI-Implementation-Plan.md)) covered the ROI review work;
this phase is a separate, explicitly requested hand-off.

## Delivered Workflow

- **Performance Specification** card: optionally attach the specification PDF
  generated by the CRM. It is validated (PDF type or extension, `%PDF-` header,
  25 MB limit) and kept as an opaque attachment. Nothing is read from it into
  the form.
- **Project Details** form: Target U-Value, Product Type, Deck Type and
  Waterproofing Type were removed (2026-11-02) because the CRM specification
  covers them (Target U Value, Tapered Insulation, Decking, Membrane). The
  removal applies to New Build and Refurbishment, which share the form. Name and
  Company stay as the Incoming Information contact. Scale and page size remain
  on the Step 1 drawing-scale selector, which the geometry depends on. The
  remaining entries are exported as a CSV.
- **Download package (.zip)**: shows a checklist of the package contents. It is
  blocked until a roof outline exists and the roof plan PDF used for that
  outline is available. A warning (not a block) appears when no specification
  PDF is attached, because the form no longer captures performance requirements.
- **Send to TaperedPlus** is inactive. It is controlled by
  `VITE_ENABLE_SEND_TO_TAPEREDPLUS` (default off). The submit handler also
  returns early while it is off, so Enter in a field cannot send. The flag
  applies to both New Build and Refurbishment because they share the form.

## Source Separation

The uploaded specification and the form are independent sources, never merged,
and do not ask for the same requirements:

- `1_spec/` holds the specification PDF byte-for-byte, under its original name.
- `2_details/project_details.csv` holds only the form entries.
- The prompt refers to both files by path and copies no values from either. It
  names the specification as the source for performance requirements (target
  U-values, tapered insulation, membrane, VCL, decking). The CSV is named as the
  source for the remaining details (contact, address, maximum insulation height,
  fall type, build method).

## Package Layout

```
TPID_<ProjectName>_<YYYYMMDD-HHmm>.zip
├── manifest.json
├── 1_spec/<original file name>.pdf          (only when attached)
├── 2_details/project_details.csv
├── 3_roof_plan/<original file name>.pdf     (each PDF that contributed a roof outline)
├── 4_drawing/
│   ├── roof_outline.dxf
│   ├── roof_outline.svg
│   ├── roof_outline.geojson
│   ├── roof_drawing.png
│   ├── roof_mask.png
│   ├── roof_metadata.json
│   └── roof_plan_marked_up_p<page>.png      (one per contributing page)
└── 5_prompt/TRICS_design_prompt.md
```

`manifest.json` lists every file with its role, media type, size and SHA-256,
the original file names, the source page of each marked-up image, and the
package (`tpid-package-v1`), drawing (`tpid-drawing-v1`) and prompt
(`trics-prompt-v2`) versions. Duplicate names receive a ` (2)` suffix.

## CSV Contract

- Columns `field_key,field_label,value`; one row per form field in form order;
  blank values are kept.
- Dropdowns are written as their visible labels (for example `MultiLayer`).
  Labels and options come from `src/lib/projectDetailsFields.ts`, which the
  form also renders from.
- UTF-8 with BOM and CRLF line endings, RFC 4180 quoting. Values beginning with
  `=`, `+`, `-`, `@`, tab or carriage return are prefixed with `'` to prevent
  spreadsheet formula execution.

## Geometry Contract

The drawing files use the same combined layout shown on Project Details,
including any roof areas dragged on that page.

- Units are millimetres, x to the right and y up, with the origin at the
  bottom-left of the exported bounds. The SVG keeps the screen's y-down
  convention with 1 user unit = 1 mm.
- Millimetres come from the paper size and drawing scale chosen at upload,
  assuming the page's long edge equals the paper's long edge. Roof areas from
  different pages are arranged side by side; their relative positions are
  illustrative. Both points are recorded in `notes`.
- DXF: AutoCAD R12 ASCII (`AC1009`) with `$INSUNITS = 4`. Layers are
  `ROOF_OUTLINE`, `CUTOUTS`, `PENETRATIONS`, `DRAINAGE_EDGES`, `OUTLETS`,
  `OUTLETS_UNCONFIRMED` and `LABELS`. Outlets are circles at their diameter;
  unconfirmed 150 mm defaults use the separate layer.
- GeoJSON: local planar millimetres, not WGS84. Roof polygons carry their
  openings as holes, with counter-clockwise exteriors per RFC 7946. Openings,
  outlets and drainage edges are also separate features.
- `roof_metadata.json`: sources and scale basis per page, roof areas (gross/net
  area, perimeter), openings, outlets, drainage edges, totals, notes, and the
  `mask_png` pixel-to-millimetre mapping.
- Raster images: `roof_drawing.png` is the Project Details drawing without grid
  or hover state. `roof_mask.png` is white roof on black with a 2% margin.
  `roof_plan_marked_up_p<page>.png` overlays the page's roof area (red),
  openings, blue drainage edges and magenta outlets on the original page image.

## Verification

```powershell
npx vitest run src/utils/projectDetailsCsv.test.ts src/utils/drawingExport.test.ts src/utils/tricsPrompt.test.ts src/utils/projectPackage.test.ts src/components/newbuild/SpecDocumentUpload.test.tsx src/components/newbuild/PackageDownload.test.tsx src/components/ProjectDetailsForm.test.tsx src/components/NewBuildApp.test.tsx
npx playwright test tests/e2e/manual-flows.spec.ts
```

The Playwright flow attaches a synthetic CRM-style specification, downloads the
package and checks every entry. It also checks that the specification and roof
plan PDFs are byte-identical, the PNG signatures, the CSV rows, the DXF version,
the metadata and the manifest. During development, both a fixture DXF (with
cutout, penetration, drainage edge and outlet) and a browser-generated DXF were
audited with `ezdxf` 1.4.5 (0 errors, 0 fixes). GeoJSON polygons were checked
as valid with Shapely.
